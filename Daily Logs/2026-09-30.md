## Work Completed

### OPNsense Segmentation Lab — VLANs, DHCP, Default-Deny Proof, and First Inter-VLAN Rule

Picked up the project from yesterday's isolated-bridge/OPNsense-install work and carried it through to a fully proven segmentation lab.

**VLAN creation and assignment:**
- Created VLAN 10 (`Servers`) and VLAN 20 (`Clients`) under Interfaces → Devices → VLAN, parented to `vtnet1` (the LAN trunk)
- Learned that creating a VLAN device doesn't make it a usable interface on its own — had to separately assign both under Interfaces → Assignments (`opt1`, `opt2`)
- Set static IPs: Servers `10.10.10.1/24`, Clients `10.10.20.1/24`

**DHCP — hit a real wall here:**
- Discovered OPNsense 26.7 has no ISC DHCPv4 service at all (removed, not just deprecated); the active service is Dnsmasq DNS & DHCP
- Configured DHCP ranges correctly, wrote a firewall rule allowing DHCP broadcasts through (via a port alias, since the port dropdown has no named DHCP/BOOTPS preset), but DHCP still didn't work
- Root cause: Dnsmasq's own interface scope was set to `LAN` only — the new VLANs were never added to it, so the service wasn't listening there at all, independent of ranges or firewall rules
- Full writeup: [OPNsense DHCP Service Confusion - ISC vs Dnsmasq vs Kea](../Troubleshooting/OPNsense%20DHCP%20Service%20Confusion%20-%20ISC%20vs%20Dnsmasq%20vs%20Kea.md)

**Test containers and default-deny proof:**
- Built `server-test` (VLAN 10) and `client-test` (VLAN 20), both lightweight Debian LXCs
- Confirmed DHCP worked on both once Dnsmasq's scope was fixed
- Pinged between them: 100% packet loss, no response — confirmed default-deny is a silent drop, not an active rejection, and reasoned through why that's deliberate (gives an attacker less information than a rejection would)

**Needed outbound access to install test software, which surfaced two more default-deny gaps:**
- No rule allowed outbound HTTP/HTTPS at all
- No rule allowed DNS queries to OPNsense's own resolver (DNS is a service OPNsense hosts, same category as DHCP)
- Added narrow rules per VLAN for each, installed nginx on `server-test`

**First real inter-VLAN rule:**
- Added a TCP rule on the Clients interface: allow traffic to `10.10.10.112/32` (the specific host, not the whole Servers subnet) on port HTTP only
- Hit a case where the rule looked completely correct and Applied, but traffic still behaved as if default-deny were still in effect — deleting and recreating the rule fixed it, likely a stale firewall-state issue rather than a config mistake. Full writeup: [OPNsense Rules Not Taking Effect Until Deleted and Recreated](../Troubleshooting/OPNsense%20Rules%20Not%20Taking%20Effect%20Until%20Deleted%20and%20Recreated.md)
- **Final proof:** `curl 10.10.10.112` from `client-test` returns nginx's page; `ping 10.10.10.112` from the same host still fails completely — the rule matches exactly what it names and nothing more

## Result

The OPNsense Segmentation Lab is complete and proven end to end: isolated sandbox, working firewall, two segmented VLANs with their own DHCP, confirmed default-deny, and a working least-privilege inter-VLAN rule. Three honest troubleshooting writeups capture the real wrong turns along the way (WAN/LAN reversed, ISC-vs-Dnsmasq confusion, stale firewall rule).
